## 2. What shipped today

Ten commits, roughly in four groups.

### Accuracy (`730a5f4`, PR #47)

- **Energy re-ranked** across the collection instead of scored absolutely.
  `rank_energy` returns `EnergyRanking { rescaled, unscored }` so tracks that
  never got a rank aren't silently left on the old scale.
- **Octave errors.** `METRICAL_RATIOS` reduced to octave relations only
  (`2.0, 0.5, 4.0, 0.25`). The 4:3 ratio was added earlier in the day on one
  track's evidence and taken back out the same day — see §5.
- **Intro contamination.** `tempo_body()` trims the intro (12%, capped 45s)
  and outro (8%, capped 30s) before estimating, with a 60s floor. Directly
  from your observation that intros mislead.
- **Second tempo opinion.** `autocorr.rs` — comb-filtered autocorrelation over
  the onset envelope, with fractional-period interpolation and a log-normal
  prior centred at 125 BPM. Independent of the beat grid. Costs 12 ms against
  ~990 ms for the rest of analysis (1.2%), so it now runs on every track.
- **Band machinery deleted.** `tempo.rs` went 430 → 121 lines. What remains is
  `TempoHint { steady_pulse }` derived from Discogs genres/styles, and it only
  influences *whether to flag*, never the number. That was your instruction and
  it is honoured literally.
- **Key detection** got graded agreement via `Camelot::compatibility()` and a
  0.6 majority-share overrule, over 8 × 30s segments.

### Portability and UI (`5fd3424`, PR #48)

You asked for 1+2+3 and got all three:

1. **Self-contained binary** — vendored aubio sources, static FFTW and
   libkeyfinder. Shared library dependencies went from 20 to 4.
2. **GitHub Releases** for distribution. No binaries in git.
3. **Web-app bridge** — the analyzer serves a local HTTP UI (hand-rolled on
   `std::net`, no dependencies) and the web app talks to it. Every CLI flag is
   exposed as a dropdown or checkbox. The oracle appears as a button only if
   it's installed locally.

### Security (during the code review)

The review found a genuine remote-code-execution-class hole and it is fixed.
The server had checked only that the peer address was loopback — worthless,
since browsers connect from loopback — and sent `Access-Control-Allow-Origin: *`.
Any website you visited could have driven the analyzer into writing arbitrary
files and running arbitrary programs. Now in `crates/cli/src/ui/origin.rs`:
Origin allow-listing, DNS-rebinding Host validation, and loopback alias
expansion so `localhost`, `127.0.0.1` and `[::1]` on one port count as one
origin. A TOCTOU race in `start_run()` (two requests could each start a
pipeline over one ledger) was fixed by claiming inside the lock.

### Speed and resilience (`e81f1ac`, `388a5dc`, `32e87cb`, `8c53795`)

- **Concurrent pipeline.** Downloads and analyses run in parallel via
  `std::thread::scope` and a bounded `mpsc::sync_channel`. Your race-condition
  concern is structurally impossible: **workers never touch the ledger.** They
  send `Done` messages; a single owner thread applies them. Runtime went from
  ~6.6 h to about an hour.
- **YouTube bot checks no longer cost a track its retries.** `StepError::blocked`
  separates "YouTube refused" from "this track failed", with
  `BLOCKED_BEFORE_GIVING_UP = 8`. Without this, one rate-limit burst would have
  written off the whole collection.
- **Cookies** accepted as a file path, a browser name, or a pasted
  "Copy as cURL". A JS runtime (deno/node/bun) is auto-detected.
- **Windows paths.** `C:\Users\...` is translated to `/mnt/c/...` under WSL.

### The oracle

`desktop-analyzer/oracle/` — Beat This! (ISMIR 2024) as a dev-only reference.
Setup, check, bench and compare scripts. Venv and corpus gitignored. A
`--disputed analysis.json` mode re-runs only the flagged tracks.

## 3. The oracle verdict on the disputed tracks

357 tracks compared (the 209 disputed plus a confirmed control group).

**The oracle is not a clean arbiter on hard material.** It fails loudly and
visibly — 5.76 BPM, 14.39, 500.00. Its own beat-gap coefficient of variation
predicts this: where its spacing is erratic (cv > 1.0) it "disagrees" with us
75% of the time; where it's steady (cv < 0.1), 19%.

Restricted to the **144 tracks where the oracle is genuinely steady**:

| | |
|---|---|
| We match it overall | 113 / 144 = **78%** |
| …on beat-grid-confirmed tracks | 98 / 101 = **97%** |
| …on disputed tracks | 14 / 42 = **33%** |
| Distance where we agree on the level | median **1.02%**, p90 2.29% |

And the confidence score is an honest self-report:

```
confidence 0.9-1.0: 129 tracks,   6 disagree  ( 5%)
confidence 0.7-0.9:  36 tracks,   9 disagree  (25%)
confidence 0.0-0.4: 192 tracks, 153 disagree  (80%)
```

That is the result worth keeping. The flags point at the right tracks. When
the analyzer says it's confident it is right 95% of the time, and when it
isn't sure it says so rather than guessing.

**A lead deliberately not acted on.** On disputed tracks the autocorrelation
matched the steady oracle 55% of the time against the beat grid's 33% —
suggesting we pick the wrong one of our own two numbers when they conflict.
But that's 29 discordant pairs, 19 vs 10, exact two-sided **p = 0.14**. Not
enough. See §5 for why this restraint matters.

## 4. The key-detection investigation

Prompted by your iOS "Song Analyzer" app disagreeing with us. Five tracks,
all at `key_strength = 1.0`, hand-checked by ear against the app.

| # | Track | We say | App said | Verdict |
|---|---|---|---|---|
| 1 | Thelma Houston – Step In | 6A | 6A, 6A (re-checked 6A) | exact |
| 2 | The Word Becomes Flesh | 3A | 3A ×4 | exact |
| 3 | Swayzak / J.B. Rose – Caught In This | 5A | 3A ×4 | disagree |
| 4 | Falke – Algebra | 12A | 3A, **12A**, 3A, 3A, 4B, 3A | disagree |
| 5 | Map.ache – Ukiu | 8B | **8A**, then 3A | relative — same notes |

**Conclusion: 3A is the app's failure output, not our error.** Every time the
app produced something other than 3A it landed on or beside our answer — 6A on
track 1, 12A on track 4, 8A (the relative minor of our 8B) on track 5. The
alternative is that four unrelated records are all A♯ minor while our detector
reads each differently and unanimously across eight independent windows.

**Decision: leave key detection alone.** The multi-profile cross-checking
design is complete and the profile values are verified (see §6), but it is not
being built against a reference whose modal output is one constant key.

**An honest caveat recorded here so it isn't forgotten:** `key_strength = 1.0`
means the eight segments *agreed with each other*, not that they were right. A
profile with a systematic bias would score 1.0 just as happily. It rules out
the track changing key mid-way — which was your original question — and
nothing more.

## 5. Mistakes made today

Recorded because the pattern in them is the useful part.

- **Added 4:3 metrical ratios on one track's evidence, then removed them.**
  Edward's Bebe is 120 — the grid says so across all 13 windows at 0.94–0.98
  confidence, while autocorrelation's 159.9 carried strength 0.26–0.36. Also
  added a strength requirement to the rescale path and blocked overruling a
  confident grid.
- **Dismissed 128.28 → 168.10 as wrong** because Discogs tagged the release
  "House". Your ground truth (167–168) proved the autocorrelation right. The
  genre assumption was the error — which is exactly why genre hints now only
  affect flagging.
- **Misdiagnosed "we double non-dance music."** Folding had fired on 1 track in
  191, and `folded_from` was null on every track blamed.
- **Claimed the second opinion cost "roughly a fifth" of analysis time.**
  Measured: 12 ms vs 990 ms. Corrected in the README.
- **Twice claimed the iOS app used non-standard Camelot labels.** It doesn't —
  A♯ minor = 3A is correct standard Camelot. A sharp was being lost in
  transcription and a theory got built on a missing character.

The common thread is acting on a single data point. The 4:3 removal and the
p = 0.14 restraint in §3 are the same lesson applied twice.
